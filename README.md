# PowerToys Triage Board — v3 (multi-member)

A static page many PowerToys maintainers can open to see **agent-produced triage
state** for open PowerToys PRs/issues and take action — post a PR review, open an
upstream PR, comment, approve a design — each **on their own behalf**. No shared
backend, no shared secret.

- **What the agents produce** → `data/` (regenerated by the board owner's job).
- **Who acts** → any signed-in member, using their own GitHub token, in-browser.
- **Data contract** → see [`SCHEMA.md`](./SCHEMA.md).
- **Live details** → full issue/PR descriptions are fetched on expansion from
  GitHub; they are not copied into generated artifacts.
- **Project tracking** → the daily updater synchronizes Microsoft project 2445:
  eligible PRs start in `To triage`, completed fork reviews move to
  `To manually review`, recognized member decisions move to `In Review` (or a
  named reviewer option), and closed/merged items move to `Done`.
- **Public skill distribution** →
  [`MuyuanMS/powertoys-dashboard-skills`](https://github.com/MuyuanMS/powertoys-dashboard-skills)
  provides an installer and canonical update prompt.
- **Dashboard controls** → **Copy update prompt** copies the current canonical
  maintenance prompt; action ratings create public issues in the skills
  repository.

## Why not "just log in with GitHub"?

GitHub Pages is static-only — it can't hold a secret, and GitHub's OAuth web
flow needs a `client_secret` (no PKCE, and the device flow is blocked by CORS).
So a **pure** static page can't do a secure "Sign in with GitHub" button. But
once a member *has* a token, the browser may call `api.github.com` directly
(GitHub allows CORS), acting as that member. That constraint drives the tiers:

| Tier | Login | Backend | Data privacy | Status |
|------|-------|---------|--------------|--------|
| **A (this build)** | member pastes a **fine-grained PAT** | none | host `data/` in a **private** repo; only members with access can `fetch` it | ✅ implemented |
| B | real "Sign in with GitHub" | 1 serverless OAuth endpoint + a GitHub App | App handles token exchange | upgrade path — UI unchanged (pluggable token) |
| C | Entra / GitHub | Azure Static Web Apps built-in auth | managed | if you want managed hosting |

The UI's token is pluggable, so moving A→B later needs **no UI rework** — only a
different way to obtain the token.

## Tier A deploy (zero backend)

1. **Create a dedicated repo** for the board, e.g. `MuyuanMS/powertoys-triage-board`.
   On the current GitHub plan, Pages requires this repo to be public. Do not
   publish tokens, credentials, or information that must remain private.
2. **Publish the UI** to GitHub Pages from that repo (or any host). Copy this
   folder's `index.html` + `data/` to the repo root / Pages source.
3. **Regenerate data** with the scheduled agent job:
   ```powershell
   pwsh -File emit.ps1        # writes data/index.json(+.js) and data/items/<n>.json
   ```
   Commit the `data/` changes. That's the only thing the schedule pushes.
4. **Each member** creates a **fine-grained PAT**:
   - Resource owner: `microsoft` (for PowerToys) **and** their fork if they open
     upstream PRs from it; or just `microsoft/PowerToys` for review/comment only.
   - Repository access: `microsoft/PowerToys` (+ `MuyuanMS/PowerToys` for PR creation).
   - Permissions: **Pull requests: Read & write**, **Issues: Read & write**,
     **Contents: Read** (Read & write only if a flow pushes commits).
   - Paste it into the board's **Sign in** modal. It's stored only in that
     member's browser `localStorage`; it is sent only to `api.github.com`.

Nothing is posted until a member turns **off** the dry-run toggle (ON by
default) and clicks an action; every write shows a payload preview first.

Project synchronization is performed by the updater, not by the static page.
It requires GitHub project permissions and never posts comments or reviews as
part of the synchronization.

## Run locally

```powershell
pwsh -File serve.ps1 -Port 8790      # http://localhost:8790/
```
`serve.ps1` is a tiny localhost static server (no token, never calls GitHub).
The page also has a `file://` fallback (`data/index.js` → `window.BOARD_INDEX`),
but serving over HTTP is recommended so `fetch` of `data/items/*.json` works.

## Files

| File | Purpose |
|------|---------|
| `index.html` | the member SPA (Alpine + Tailwind via CDN) |
| `emit.ps1` | regenerates `data/index.json` + `data/items/<n>.json` from agent output |
| `serve.ps1` | local static server for development |
| `data/index.json` / `.js` | slim backlog list (all items) |
| `data/items/<n>.json` | latest agent artifact per issue/PR number |
| `SCHEMA.md` | full data contract + action semantics |

## Safety model

- **Dry-run ON by default** — non-GET calls are intercepted and previewed, not sent.
- **Read-only without login** — suggestions and proposed comments load when an
  item is expanded; login is required only for actions. If the board data is
  hosted privately, the hosting layer must grant viewers access to the static
  files or provide an authenticated data endpoint.
- **Per-member tokens** — no shared secret; the page can't act on its own.
- **Members act as themselves** — reviews/PRs/comments are authored by whoever clicks.
- **Staleness guard** — if upstream has new commits since the agent's `head_sha`,
  the item is flagged "re-run before posting."
- **Live detail reads** — expanding an item fetches its current GitHub issue/PR
  body and metadata; unauthenticated reads work with the public rate limit, while
  a member PAT provides a higher rate limit.
